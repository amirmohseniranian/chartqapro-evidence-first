# ChartQAPro Evidence-First Reasoning

Deterministic, reproducible evaluation of vision-language models on ChartQAPro with a controlled comparison between direct chart question answering and an explicit **Evidence-First Reasoning (EFR)** pipeline.

## Abstract

This project studies whether forcing a vision-language model (VLM) to first extract concise, chart-supported evidence and only then produce the final answer provides a useful alternative to direct end-to-end chart question answering.

The implementation evaluates two conditions:

1. **Direct QA** — the model receives the chart and question and returns the final answer.
2. **Evidence-First Reasoning (EFR)** — the model first extracts structured evidence and explicitly described operations from the chart, after which a second text-only generation stage produces the final answer from the evidence JSON.

The primary experiment uses `Qwen/Qwen2.5-VL-3B-Instruct` on the full ChartQAPro test split. A secondary comparison uses `HuggingFaceTB/SmolVLM2-2.2B-Instruct` on a deterministic 300-example stratified subset containing all five ChartQAPro question types.

The implementation is designed as a research-grade benchmark runner rather than a minimal inference script. It locks the experimental protocol, verifies dataset and evaluator integrity, normalizes benchmark fields explicitly, records runtime provenance, supports resumable JSONL prediction files, validates prediction coverage before scoring, mirrors the repository evaluator's actual scoring call, performs paired per-example analysis, and generates figures only from complete evaluations.

> **Scientific status:** This repository contains the experimental protocol and execution machinery. Final benchmark scores must be generated by executing the benchmark on a compatible runtime; the uploaded source contains no embedded execution output that independently justifies inventing or reporting unobserved results.

## Research Question

The central comparison is:

> Does an explicit evidence extraction bottleneck improve chart-question answering relative to direct answer generation under the same model, benchmark, answer semantics, and generation protocol?

The comparison is intentionally controlled. The scientific intervention is the additional evidence-generation stage; performance engineering is treated separately from task semantics.

## Scientific Background

### Chart Question Answering

Chart question answering requires a model to combine visual perception with language understanding and, in some cases, numerical reasoning. The input consists of a chart image and a natural-language question. A correct response may require reading labels, identifying values, comparing categories, following conversational context, or performing a calculation supported by chart values.

The implementation treats the benchmark as a constrained evaluation problem rather than unconstrained visual-language generation. Prompts therefore encode the answer format associated with each question type.

### Direct QA

In the Direct condition, the VLM receives:

* the chart image,
* the normalized question or conversation,
* a question-type-specific instruction.

The model is asked to produce only the final answer.

The direct condition is intentionally simple because it is the baseline against which the evidence bottleneck is compared.

### Evidence-First Reasoning

EFR decomposes inference into two stages:

```text
Chart image + question
        |
        v
Evidence extraction
        |
        v
Structured evidence JSON
        |
        v
Text-only answer generation
        |
        v
Final answer
```

The evidence stage is instructed to:

* extract only chart-supported observations,
* separate observed facts from derived operations,
* avoid unsupported values,
* mark insufficient support explicitly,
* provide a tentative answer candidate only when justified.

The answer stage then receives the question plus the evidence JSON and is prohibited from introducing information outside that evidence.

This is a **model-generated reasoning bottleneck**, not a gold evidence annotation. The evidence produced by the first stage must never be interpreted as ground-truth supervision.

## Methodology

### 1. Deterministic Experiment Lock

The benchmark protocol is captured in `EXPERIMENT_LOCK` and versioned by `PROTOCOL_VERSION`. The protocol hash is computed from the protocol material and prompt configuration.

The locked configuration includes:

* random seed,
* model identifiers,
* generation limits,
* padding policy,
* batch policy,
* cache configuration,
* text and multimodal batch sizes,
* execution optimization version,
* Qwen image-resolution bounds.

Prediction files carry the protocol hash so that outputs generated under an incompatible protocol cannot silently participate in a resumed run.

### 2. Dataset Acquisition and Integrity

The experiment uses the ChartQAPro dataset identified as:

```text
ahmed-masry/ChartQAPro
```

The source parquet is:

```text
data/test-00000-of-00001.parquet
```

The code:

1. mounts Google Drive for persistent experiment storage;
2. downloads the exact parquet only when the stored archive is absent or fails integrity verification;
3. computes a SHA-256 digest of the parquet;
4. stores the verified parquet inside a `ZIP_STORED` archive;
5. records the dataset hash, archive size, dataset identifier, and creation timestamp;
6. re-verifies the archive and parquet hash before reuse.

This makes a resumed experiment dependent on the same verified data artifact rather than on an implicitly changing local cache.

### 3. Dataset Normalization

ChartQAPro fields can arrive as Python sequences, NumPy values, Pandas values, serialized list strings, dictionaries, byte containers, data URIs, or file references. The implementation therefore normalizes the representation before prompt construction.

Core normalization functions include:

* `to_python`
* `parse_listish_text`
* `normalize_serialized`
* `as_string_list`
* `question_for_prompt`
* `answer_list`
* `year_flag_list`
* `image_bytes_from_value`
* `decode_chart_image`

For conversational questions, all previous turns are preserved and the final turn is marked explicitly as the target question.

Answers and year flags are retained as Python lists so the evaluator-facing JSON preserves the expected sequence structure.

### 4. Image Validation and Caching

Each image is:

1. converted to raw bytes,
2. decoded with Pillow,
3. loaded to verify decodability,
4. converted to RGB,
5. measured for width, height, and pixel count,
6. hashed with SHA-256,
7. cached in its original encoded form,
8. cached again as lossless RGB PNG.

The RGB cache is an execution optimization. It avoids repeated JPEG/WEBP decoding and RGB conversion without changing model-side resize parameters or tensor semantics.

A deterministic sample identifier is derived from the source row index, normalized question, and image bytes:

```text
sample_id = row_<zero-padded-row-index>_<first-12-hex-digits-of-SHA256>
```

The exact hash inputs are fixed by the implementation and are not intended as a cryptographic identity mechanism; they provide stable benchmark bookkeeping.

### 5. Dataset Audit

The preprocessing stage records:

* row count,
* column count,
* image decodability,
* image decode failures,
* duplicate question-image pairs,
* missing questions,
* missing answers,
* missing question types,
* missing year flags,
* missing images,
* observed question-type values,
* observed year values.

The normalized working table is then checked for:

* one row per source example,
* non-empty sample IDs,
* unique sample IDs,
* non-empty questions,
* non-empty answer lists,
* non-empty year lists,
* valid cached image files.

### 6. Prompt Construction

The prompt layer is explicitly type-aware.

#### Direct prompts

Direct prompting requires the model to use only information supported by the chart and question. It is instructed not to invent values, labels, years, or relationships and to return `unanswerable` when the chart is insufficient.

Format constraints include:

* short answer for Factoid and Hypothetical,
* conversation-aware answer for Conversational,
* exactly one option letter for Multi Choice,
* exactly `true` or `false` for Fact Checking.

#### EFR evidence prompts

The evidence stage always requests a JSON object with exactly five top-level fields:

```text
answer_type
evidence
operations
support_status
answer_candidate
```

The semantics are:

* `answer_type`: semantic answer category or `unanswerable`;
* `evidence`: chart-supported observations only;
* `operations`: calculations or transformations that are justified by the evidence;
* `support_status`: whether the evidence is sufficient;
* `answer_candidate`: tentative answer only when supported.

#### EFR answer prompts

The second stage receives the original question plus the evidence JSON. It is instructed to return only the final answer and to return `unanswerable` when the evidence is insufficient.

This creates the intended information boundary:

```text
Visual input -> evidence representation -> final textual answer
```

### 7. Safe Template Rendering

The EFR JSON schema contains literal braces. Using normal `str.format()` would treat those braces as formatting fields.

The implementation therefore uses `render_template`, which replaces only explicitly named placeholders. A sanity check confirms that literal JSON braces and the question text survive template rendering.

### 8. Model Loading

The primary model path uses:

```text
Qwen2.5-VLForConditionalGeneration
AutoProcessor
qwen-vl-utils
```

The secondary model path uses:

```text
AutoModelForImageTextToText
AutoProcessor
```

On CUDA-capable systems, the configured quantization is:

```text
4-bit loading
NF4 quantization
double quantization
FP16 compute
```

The models are placed on a single active device. Models are switched only when needed, and the loaded model is reused across Direct and EFR conditions within a suite.

### 9. Attention and Generation Policy

Scaled Dot Product Attention is enabled when supported by the runtime. The code falls back to the default attention implementation if the installed model/runtime combination rejects the SDPA argument.

`torch.compile` is disabled by default because generation uses variable shapes and because the benchmark prioritizes stable execution semantics over an unverified compilation path.

Generation runs under `torch.inference_mode()` with `use_cache=True`.

Sampling is disabled:

```text
do_sample = False
```

Although `TEMPERATURE = 0.0` is stored in the experiment configuration, the generation helper passes `temperature` only when sampling is enabled. Therefore the actual deterministic path does not use temperature scaling.

### 10. Left-Padded Batched Generation

The tokenizer is explicitly configured for left padding, and generation refuses to proceed if a valid `pad_token_id` cannot be established.

For a padded batch, the generated sequence is trimmed after the common padded input width:

```text
prompt_len = inputs["input_ids"].shape[-1]
generated_only = output_ids[:, prompt_len:]
```

This is critical because batch decoding must remove the entire padded prompt region before decoding the newly generated tokens.

### 11. Qwen2.5-VL Image Resolution Bounds

The Qwen processor is configured with:

```text
min_pixels = 256 × 28 × 28
max_pixels = 1280 × 28 × 28
```

These bounds constrain visual tokenization cost while preserving the experiment's fixed preprocessing policy.

### 12. SmolVLM2 Compatibility Layer

The secondary runner contains a dedicated compatibility layer for SmolVLM2.

It:

* uses local filesystem image paths,
* routes processor-only arguments through `processor_kwargs`,
* synchronizes `pad_token_id` between tokenizer, model configuration, generation configuration, and nested text configuration,
* enforces left padding,
* fixes the processor's frame/FPS defaults,
* bypasses expensive adaptive multimodal batch probing,
* restores the original notebook globals after the secondary run.

The secondary benchmark therefore uses the same scientific prompts, generation limits, evaluator semantics, and stratified subset while adapting only model-interface details.

## Mathematical Details

### Paired Effect Estimate

When both primary conditions are complete, the code computes a per-example score difference:

```text
Δᵢ = sᵢ(EFR) − sᵢ(Direct)
```

where:

* `i` indexes a benchmark example,
* `sᵢ(EFR)` is the evaluator score for EFR,
* `sᵢ(Direct)` is the evaluator score for Direct QA.

The paired mean difference is:

```text
Δ̄ = (1 / N) Σᵢ Δᵢ
```

A positive value means that EFR receives the higher score on average among the paired examples.

### Bootstrap Interval

The paired bootstrap uses 10,000 resamples generated with NumPy's `default_rng` and the experiment seed.

For bootstrap replicate `b`:

```text
Δ̄*ᵦ = (1 / N) Σⱼ Δᵢⱼ
```

The reported percentile interval is:

```text
95% interval = [Q₀.₀₂₅(Δ̄*), Q₀.₉₇₅(Δ̄*)]
```

The code generates bootstrap replicates in chunks of 500 so that the full resampling matrix is not materialized simultaneously.

This interval is a bootstrap uncertainty summary for the paired mean difference; it is not a claim of causal identification.

### Static Performance-Engineering Score

The notebook also computes a static implementation-quality score from ten observable engineering dimensions.

The score is:

```text
Score = Σᵢ wᵢ × rᵢ / 100
```

where:

* `wᵢ` is the fixed dimension weight,
* `rᵢ` is the fixed 0–100 implementation sub-score,
* the weights sum to 1000.

The configured dimensions and weights are:

| Dimension                       | Weight |
| ------------------------------- | -----: |
| Batching                        |    180 |
| Model lifecycle                 |    120 |
| CPU / I/O                       |    140 |
| Transfer and synchronization    |    120 |
| Memory                          |    100 |
| Kernel / API usage              |    100 |
| Algorithmic work                |     80 |
| Persistence                     |     60 |
| Correctness and reproducibility |     60 |
| Measurement hygiene             |     40 |

The source computes:

```text
Static score, original-style implementation: 866
Static score, optimized implementation: 944
```

These values are **not benchmark accuracy or runtime speed measurements**. The implementation explicitly marks empirical T4 speedup as unmeasured unless the runtime benchmark is actually executed.

## Evaluation Protocol

### Evaluator Handling

The code downloads and preserves the exact evaluator source used by the repository-oriented scoring path, stores its SHA-256 hash, and imports the saved evaluator locally.

Before accepting benchmark scores, the code runs perfect self-match probes for every question type.

It then verifies that:

* evaluator input uses list-valued `Answer`,
* evaluator input uses list-valued `Year`,
* `Question Type` is a string,
* prediction is a string,
* detailed per-example scores reproduce the evaluator's aggregate split scores,
* the overall detailed mean reproduces the evaluator's overall score.

The detailed-score implementation intentionally mirrors the evaluator's actual function call rather than introducing an independent interpretation of the benchmark metric.

### Coverage Gate

A benchmark is scoreable only when the prediction set satisfies all of the following:

```text
missing current-protocol examples = 0
unexpected successful examples = 0
duplicate successful sample IDs = 0
incompatible protocol records = 0
successful records = expected records
```

Incomplete runs are written as `INCOMPLETE` reports and are not converted into benchmark scores.

### Prediction Resume Semantics

A prediction record counts as completed only when:

```text
status == "ok"
```

and the record belongs to the current protocol hash.

Failed records remain retryable.

If a prediction file contains records from an incompatible protocol, the old file is moved to a deterministic stale-file name rather than being silently mixed with the new run.

## Performance Engineering

The benchmark separates scientific semantics from execution optimization.

### Adaptive Multimodal Batch Tuning

For the primary model, candidate batch sizes are probed on representative examples selected by image pixel footprint.

The policy:

1. determines a hardware-dependent candidate range;
2. tests every candidate size rather than skipping intermediate values;
3. records elapsed time and peak reserved GPU memory;
4. rejects candidates that violate the configured memory-headroom policy;
5. selects the highest-throughput stable batch size;
6. uses larger batch size as a deterministic tie-breaker;
7. persists the selection using a runtime-specific cache key.

For a T4-class device, the configured upper bound is 6.

The tuning key includes:

* model ID,
* GPU identity,
* PyTorch version,
* generation stage,
* token budget,
* protocol hash,
* tuning version.

### Memory Headroom

The configured memory headroom fraction is:

```text
0.12
```

A candidate is considered memory-safe only when its observed reserved memory and post-probe free memory satisfy the corresponding thresholds.

### OOM Recovery

CUDA out-of-memory failures are handled recursively:

```text
batch
  |
  +-- OOM --> split into two smaller batches
                |
                +-- retry recursively
```

If a single example still fails, the runner retries with the configured fallback token budget.

Successful retry metadata is recorded so an earlier larger-batch OOM does not make a later successful prediction appear failed.

### EFR Text Batching

EFR evidence generation is multimodal and batched.

Once evidence has been parsed successfully, the final answer stage is text-only. Answer tasks accumulate across multimodal evidence batches and are processed in micro-batches of up to 16 prompts.

Within each text micro-batch, prompts are sorted by character length to reduce unnecessary padding.

### Model Lifecycle

Each model suite loads the model once and reuses it for both Direct and EFR conditions.

The GPU allocator is not flushed after every generation. Explicit cache clearing is reserved for:

* model switching,
* OOM recovery,
* calibration boundaries.

### Persistence

Prediction JSONL files are written through `JsonlWriter`.

When the destination is on Google Drive:

```text
inference process
      |
      v
local buffered spool
      |
      v
periodic byte-range checkpoint
      |
      v
Drive append + fsync
```

This reduces frequent Google Drive filesystem synchronization while preserving resumability.

### Timing Hygiene

Optional benchmarks use:

* synchronized CUDA timing,
* identical warmup policy,
* repeated measurements,
* median, mean, minimum, and maximum runtime summaries.

GPU execution is synchronized before and after timed calls so asynchronous CUDA launches do not contaminate wall-clock measurements.


## Limitations

### 1. Colab-Centric Execution

The source explicitly depends on Google Colab components such as Google Drive mounting and browser download helpers. It is therefore not a drop-in standalone Python package.

### 2. Two-Stage EFR Is More Expensive

EFR requires an additional multimodal generation stage and a text-only generation stage. Any accuracy gain must therefore be interpreted together with latency and compute cost.

### 3. Generated Evidence Is Not Ground Truth

The EFR evidence is produced by the model itself. A well-structured evidence object does not prove that every extracted fact is correct.

### 4. Secondary Model Uses a Subset

SmolVLM2 is evaluated on only 300 stratified examples. Its results should not be compared with the full-split Qwen result as though the evaluation populations were identical.

### 5. Batch Optimization Is Runtime-Dependent

The selected multimodal batch size depends on hardware memory, software versions, token budget, and measured throughput. A batch size that is optimal on a T4 may not be optimal elsewhere.

### 6. Static Performance Score Is Not Empirical

The 866-to-944 engineering score is a static implementation assessment. It is not a claim about actual acceleration, tokens per second, energy use, or wall-clock speedup.

### 7. Benchmark-Specific Prompting

The prompts are intentionally aligned with ChartQAPro's question types and expected answer formats. They should not be assumed to transfer unchanged to another chart benchmark.

### 8. Evaluator Fidelity

The implementation deliberately mirrors the repository evaluator's actual scoring call rather than silently rewriting benchmark semantics. This preserves reproducibility with the selected evaluator path but also means that any behavior of that evaluator is inherited by the reported scores.

## Future Work

The current implementation provides a controlled baseline for several stronger research directions.

### Evidence Quality and Faithfulness

A future study could separately evaluate:

* evidence extraction accuracy,
* numerical operation correctness,
* evidence completeness,
* evidence faithfulness,
* answer consistency conditional on evidence quality.

The current benchmark does not contain gold evidence annotations, so these should be introduced as separate evaluation tasks rather than inferred from final answer accuracy.

### Ablation Studies

Useful controlled ablations include:

```text
Direct
Direct + explicit format constraints
EFR with observations only
EFR with observations + operations
EFR with answer candidate
EFR with evidence validation
```

These would distinguish whether performance changes come from structured visual extraction, explicit numerical operations, or merely additional prompting.

### Cost-Aware Evaluation

Future reports should include:

* wall-clock latency,
* tokens generated,
* GPU memory peak,
* examples per second,
* energy or accelerator utilization when available.

Accuracy and efficiency should then be analyzed jointly.

### Cross-Model Generalization

The same protocol can be extended to additional VLMs while preserving:

* the same ChartQAPro split,
* the same question-type semantics,
* the same output normalization,
* the same evaluator,
* the same paired-analysis framework.

### Stronger Evidence Validation

A future EFR variant could add a third stage that mechanically validates extracted numbers, units, and chart relationships before the final answer is produced.

### Statistical Extensions

Future studies could complement the paired bootstrap with:

* permutation tests,
* stratified bootstrap intervals,
* question-type interaction analysis,
* effect-size distributions,
* multiple-comparison correction for a large ablation suite.

## Research Interpretation

The implementation should be interpreted as a **controlled evaluation of reasoning decomposition**, not as a claim that the EFR prompt itself constitutes a new model architecture.

The main scientific contribution of the experiment design is the separation of:

```text
visual evidence extraction
```

from

```text
final answer generation
```

while keeping the benchmark, model, output constraints, evaluator, and protocol otherwise fixed.

This separation makes it possible to ask a precise empirical question:

> When a VLM is required to expose a compact evidence representation before answering, does final chart QA performance improve, degrade, or remain unchanged?

That question can be evaluated without treating the generated evidence as ground truth.
